동물병원 300개 지점을 24시간 운영하는 펫 클리닉이, 병원 직원용 홈페이지(PetClinic)의 인프라를 AWS에 구축해 달라고 의뢰했다.

50초. 왼쪽 열(받은 요구)을 읽고, 오른쪽 열은 “뒤에서 담당자가 하나씩 설명한다”로 넘긴다. 2분 근거: WAS 대상은 상태 확인 2회 실패(약 40초)로 빠지고 남은 서버가 처리한다. DB 장애 조치는 보통 60~120초다. 질문이 나오면 이 두 숫자로 답한다. 앱을 만드는 프로젝트가 아니라 이미 있는 PetClinic을 운영할 인프라를 짓고 배우는 프로젝트라는 점도 한 문장 넣는다.

45초. 그림을 위에서 아래로 한 번 훑는다. 가로 배치 설계도가 완성되면 그림을 교체하고, 이 슬라이드는 그림을 위에 크게, 표와 핵심 결정을 아래에 두는 배치로 바꾼다. 요청이 CloudFront부터 DB까지 일곱 구간을 지난다는 것, 그리고 오른쪽 상자의 세 가지 결정만 강조한다. VPC 오리진을 쓰지 않은 이유(정액 요금제 Business 이상 필요)는 질문이 나오면 답한다.

WAS

호환성 검토와 프레임워크 취약점 보완

버전 호환성

  • 기존 Java 8, javax 기반 소스와의 호환성을 고려해 Tomcat 9.0.122, Spring Framework 5.3.39 적용
  • Spring BOM으로 Spring 모듈 버전 통일
  • Java 패키지 버전 고정으로 검증되지 않은 업데이트 방지

취약점 보완

  • 업데이트 후에도 잔존하는 프레임워크 취약점의 실제 사용 조건 확인
  • CVE-2024-38820과 관련된 DataBinder 차단 목록 설정을 입력 허용 목록 방식으로 변경
  • 추가로 확인한 hidden ID 변조 문제에 URL의 petId 사용, 보호자와 반려동물 관계 검증 적용
  • 수정 후 전체 테스트 통과, WAR 빌드 확인

저는 기존 Petclinic을 AWS 3티어 환경에서 운영하기 위한 WAS 구축과 배포를 담당했습니다.

먼저 기존 소스와의 호환성을 고려해 Java 8, Tomcat 9, Spring Framework 5.3.39를 적용했습니다. 의존성 버전을 통일하고, 프레임워크 취약점과 잘못된 반려동물 정보가 수정되는 문제도 보완했습니다.

Arm 기반 배포와 설정 외부화

Arm 기반 배포

  • Amazon Linux 2023, Graviton 기반 t4g.small 적용
  • SSM을 통한 WAR 전송과 Tomcat 배포
  • systemd를 통한 부팅 시 자동 시작과 서비스 관리
  • Arm 환경에서 Java, Tomcat 기동과 PetClinic, DB 연동 확인

설정 외부화

  • Tomcat의 setenv.sh에서 Parameter Store의 DB 접속 주소와 Secret ARN 조회
  • 조회한 설정을 Java 시스템 속성으로 PetClinic에 전달
  • Secrets Manager JDBC 드라이버를 통한 DB 자격 증명 조회
  • DB 접속 설정 변경 시 WAR 재빌드 없이 Tomcat 재시작으로 반영

배포 환경은 비용 효율을 고려해 Amazon Linux 2023과 ARM 기반 t4g.small을 선택했습니다. SSM으로 WAR 파일을 전송하고, systemd를 통해 EC2 부팅 시 Tomcat이 자동으로 시작되도록 구성했습니다.

또한 DB 접속 설정을 소스에서 분리했습니다. Tomcat 시작 시 setenv.sh에서 Parameter Store의 설정을 읽고, Secrets Manager JDBC 드라이버로 DB 자격증명을 조회하도록 연동했습니다.

가용성 확보와 자동 확장

가용성과 자동 확장

  • 2a, 2c 가용 영역에 WAS 분산 배치
  • 내부 ALB를 통한 요청 분산과 상태 확인
  • AMI와 시작 템플릿 기반 ASG, CPU 기준 자동 확장 구성

모니터링과 알림

  • EC2 CPU와 ALB 응답 시간, 요청량, 오류, 정상 대상 수 확인
  • CloudWatch 에이전트로 메모리 사용률 수집
  • HealthyHostCount가 2 미만이면 CloudWatch 경보와 SNS 이메일 알림
  • whoami.jsp에서 AWS API로 조회한 대상 그룹 상태와 현재 요청 경로 시각화

가용성을 위해 2a와 2c에 WAS를 분산 배치하고, Internal ALB를 통해 요청을 분산했습니다. 구성한 서버를 AMI와 시작 템플릿으로 만들어 CPU 부하에 따라 ASG가 자동으로 확장되도록 했습니다.

운영 상태는 EC2 CPU와 ALB 지표로 확인하고, CloudWatch Agent로 메모리 사용률을 추가 수집했습니다. 정상 WAS가 한 대 이하로 줄어들면 CloudWatch 경보와 SNS 이메일 알림을 받도록 구성했습니다.

마지막으로 ALB의 요청 분산과 타겟그룹 상태를 한눈에 볼 수 있는 검증 페이지를 직접 구성했습니다. 현재 응답한 서버와 각 대상의 상태를 표시해, 부하 분산과 자동 확장 결과를 시각적으로 확인했습니다.

DB 서버

RDS MySQL과 RDS Proxy

안정적인 DB 운영을 위해 가용성과 연결 안정성을 중점적으로 고려했다.

RDS for MySQL 8.4

  • Multi-AZ: AZ 2a Primary / AZ 2c Standby (동기 복제)
  • MySQL 8.4 LTS: 장기 지원과 유지보수 고려
  • 인스턴스: db.t4g.small / gp3 20 GiB
    • 사전 부하 테스트 연결 사용률: micro 93%, small 56%
  • 데이터 보호: 자동 백업 7일 / KMS 스토리지 암호화

RDS Proxy

  • 연결 경로: WAS → RDS Proxy → RDS
  • 연결 풀링과 재사용: WAS 확장 시 DB 연결 증가 대응
  • 장애 대응: Multi-AZ 장애 조치 시 DB 연결 복구 지원
  • TLS 필수: DB 인증 정보와 전송 데이터 보호
  • 최대 연결 비율 80%: 다른 DB 접속을 위한 연결 여유 확보

안녕하십니까. 데이터베이스 구축을 담당한 우수빈입니다.

저희는 안정적인 DB 운영을 위해 가용성과 연결 안정성에 중점을 두었습니다.

먼저 장애 발생 시 자동으로 다른 가용 영역으로 전환할 수 있도록 Multi-AZ를 적용하고, 장기적인 유지보수를 고려해 MySQL 8.4 LTS를 선택했습니다.

인스턴스는 비용 효율적인 T4g 계열을 검토했으며, 사전 부하 테스트에서 micro의 연결 사용률은 93%, small은 56%로 나타나 자원 여유가 큰 t4g.small을 선정했습니다.

또한 WAS 확장에 따른 DB 연결 증가에 대응하고, 장애 조치 시 연결 복구를 지원하기 위해 RDS Proxy를 도입했습니다.

RDS Proxy와 Secrets Manager를 연동하는 과정에서 IAM 권한과 보안 그룹 설정이 DB 연결에 미치는 영향을 직접 확인하며, 보안과 접근 제어의 중요성을 체감했다.

다음은 DB 보안 구성입니다.

관리자 계정과 앱 계정을 분리해 필요한 권한만 부여했고, 비밀번호를 안전하게 관리하기 위해 Secrets Manager를 사용했습니다.

또한 WAS가 DB에 직접 접근하지 않고, RDS Proxy를 거치도록 보안 그룹을 설정했습니다.

WAS가 확장될 때 데이터가 다시 초기화되지 않도록 설정하고, 부하 테스트를 위해 데이터 10만 건을 별도로 적재했습니다.

DB 계정을 분리하고 RDS Proxy로 접근 경로를 제한하면서, 단순한 연결 성공보다 안전한 연결 구조를 만드는 것이 중요하다는 점을 배웠습니다.

이상으로 DB 발표를 마치겠습니다. 이어서 WEB 담당자가 발표하겠습니다.

웹 서버와 CloudFront

Apache 리버스 프록시

<VirtualHost *:80>
    ProxyAddHeaders On
    ProxyPreserveHost On
    RewriteEngine On
    # /petclinic 으로 오면 /petclinic/ 으로 301
    RewriteRule ^/petclinic$ https://%{HTTP_HOST}/petclinic/ [R=301,L]
    # ttl=55: ALB 유휴 제한(60초)보다 먼저 닫는다
    # addressttl=30: ALB IP가 바뀌어도 30초 안에 다시 조회
    ProxyPass        "/petclinic/" "http://<INTERNAL_ALB_DNS>/petclinic/" ttl=55 addressttl=30
    ProxyPassReverse "/petclinic/" "http://<INTERNAL_ALB_DNS>/petclinic/"
</VirtualHost>
  • /petclinic/만 WAS로 넘기고, 나머지는 Apache가 직접 응답
  • 내부 ALB는 IP가 아니라 DNS 이름으로 가리킨다.
  • SELinux에서 httpd_can_network_connect 허용

45초. ttl을 ALB 유휴 시간보다 짧게 두는 이유(ALB가 먼저 끊은 연결을 다시 쓰면 502)를 한 문장으로.

CloudFront와 외부 ALB 보호

CloudFront (정액 요금제 Free)

  • 사용자 구간만 HTTPS. ALB에는 인증서가 없어 오리진은 HTTP
  • 동적 페이지라 캐싱 비활성화, 쿼리 문자열과 쿠키는 모두 전달
  • 오류 시 S3의 공통 오류 페이지 (/pet_*, OAC)
  • WAF 속도 제한: IP마다 5분에 300건 (현재 모니터 모드)

외부 ALB에 CloudFront만 닿게

  1. 보안 그룹: CloudFront 관리형 접두사 목록만 허용
  2. 리스너: 비밀 헤더를 포함한 요청만 전달, 나머지는 403

접두사 목록은 다른 사람의 CloudFront 배포도 통과시킨다. 비밀 헤더가 우리 배포만 골라낸다.

45초. VPC 오리진을 쓰면 ALB를 internal로 둘 수 있지만 정액 요금제 Business(월 200 USD) 이상이 필요해서 internet-facing ALB + 두 겹 보호를 택했다고 말한다.

배운 점과 남은 과제

배운 점

  • 구축보다 이유를 설명하는 것이 어렵다. 모든 설정 값에 근거를 기록했다.
  • 절차서를 타인이 수행해 보면 누락된 단계가 드러난다.

남은 과제

  • ssm 엔드포인트가 AZ A에만 존재하여, AZ A 장애 시 신규 WAS의 설정 조회 실패 가능 → AZ C 추가
  • WAF 속도 제한을 모니터 모드에서 차단 모드로 전환
  • WAS 정상 대상 수 경보 (SNS 이메일)
  • 수작업 구축을 IaC로 옮기기

15초. 남은 과제를 스스로 말하면 질문이 그쪽으로 오기 쉽고, 답도 준비되어 있다.

최종 결과물

  • 설계도: 3계층, AZ 두 곳, NAT 게이트웨이 없는 구성
  • IP 주소 지도와 보안 그룹: 서브넷 14개, 앞 계층만 허용하는 보안 그룹 사슬
  • VPC 엔드포인트: ssm, ssmmessages, secretsmanager, monitoring, S3
  • 절차서: 구축 단계 전체와 정책 파일, 설정 파일 (GitHub 저장소와 Wiki)
  • WAS 대시보드: 요청을 처리한 WAS와 대상 상태 → 시연에서 확인

15초. 마지막 항목을 말하면서 시연으로 넘어간다.

한 연결의 양단에서 수신 측의 유휴 시간을 송신 측보다 길게 설정한다. 수신 측이 먼저 연결을 종료하면 이미 종료된 연결로 요청이 전송되어 ALB가 502를 반환한다.

응답 대기 상한은 CloudFront 30초, ALB 60초다. 그러므로 40초가 소요되는 조회는 CloudFront가 먼저 연결을 종료한다. GET과 HEAD는 재시도하고, POST는 재시도하지 않는다.

측정한 값

  • 장애 조치 시험의 SQL 연결 복구: RDS Proxy 경유 13초, 직접 연결 135초
  • 전체 웹 서비스 복구 시간이 아니라 SQL 연결 기준

WAS 서버 하나가 고장 나면

  • 상태 확인 20초 간격, 2회 실패로 약 40초 후 대상에서 제외된다.
  • 남은 WAS가 요청을 받고, Auto Scaling 그룹이 교체한다.

RTO (Recovery Time Objective, 복구 시간 목표)와 RPO (Recovery Point Objective, 복구 시점 목표)는 조직이 정하는 목표다. AWS 문서가 주는 것은 그 목표를 맞추는 데 쓸 수치와 작동 방식이다. RDS 가이드는 MySQL의 RPO를 수치로 적지 않는다. 그래서 작동 방식만 말한다.
