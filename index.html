아키텍처: 사용자 요청 경로

  • CloudFront와 WAF: 사용자 요청을 HTTPS로 받고, WAF가 IP마다 요청 수를 제한한다.
  • ① 캐시 미스: 본 프로젝트에서는 요청이 대부분 VPC로 전달된다.
  • ② 오류: 403, 404, 5xx 등 오류 코드로 응답하려고 할 때 S3에 저장된 페이지로 응답한다.
  • 패키지 버킷 (요청 경로 외): 패키지 관리자로 받을 수 없는 패키지를 수동으로 설치할 때 S3 게이트웨이 엔드포인트로 받는다.

30초.

  1. 아키텍처와 작업 기반을 설명할 김태준입니다. 먼저 아키텍처입니다. 사용자 요청이 클라우드프론트에 도착하면 방화벽이 요청을 검사해 통과시키거나 차단합니다.

  2. 1번은 캐시 미스 경로로 본 프로젝트에서는 대부분 이 경로로 전달됩니다.

  3. 2번은 오류 경로로 요청이 차단되거나 오리진이 특정 상태 코드를 반환하면 S3에 저장된 파일로 응답합니다.

  4. 한편 패키지 버킷은 사용자 요청과 무관한, 수동 설치 패키지 저장소입니다.

질문 대비: 오류 페이지(/pet_*)는 CachingOptimized로 캐싱되므로, 이미 캐싱된 페이지는 S3에 다시 접근하지 않는다.

WAF = Web Application Firewall HTTPS = HTTP Secure IP = Internet Protocol

아키텍처: VPC 내부 구성

20초.

  1. VPC 내부는 이렇습니다. 가용 영역 두 개를 사용했으며, 서브넷 IP 대역을 축약 표기 했으며 주로 슬래시 27이나 슬래시 28 크기입니다. 다른 가용 영역도 둘 수 있도록 설계했기 때문에 빈 IP 대역이 존재합니다.

  2. 퍼블릭 서브넷에는 외부 ALB만 두었습니다.

  3. 웹 서버와 WAS는 오토 스케일링 그룹으로 개수가 관리되고 그 사이에 내부 ALB가 있습니다.

  4. WAS는 RDS Proxy를 거쳐 Primary DB에 접속합니다.

  5. 이 구조에서 AWS 서비스는 VPC 엔드포인트로 호출합니다.

질문 대비: Primary DB 장애 시에는 Standby DB가 새 Primary DB로 승격된다. 질문 대비: S3 게이트웨이 엔드포인트는 라우팅 테이블 항목이라 엔드포인트 서브넷에 없다. 질문 대비: ALB는 /27 이상에 여유 IP 8개, RDS Proxy는 db.*.xlarge 이하에서 여유 IP 10개가 필요하다. 질문 대비: 충돌 가능성이 높은 사설 IP 대역은 회피했다. 회피한 대역(설계 기준 문서): EKS 기본 서비스 대역 172.20.0.0/16, 10.100.0.0/16, Docker 기본 브리지 172.17.0.0/16, 가정용 공유기에서 흔한 192.168.0.0/24, 192.168.1.0/24, 10.0.0.0/24 등.

IGW = Internet Gateway

작업 기반: 보안 그룹 사슬과 관리 접속

CloudFront접두사 목록 80 외부 ALB 80 웹 서버 80 내부 ALB 8080 WAS 3306 RDS Proxy 3306 RDS 443 443 VPC 엔드포인트ssm, ssmmessages, secretsmanager, monitoring
  • 각 구성 요소는 바로 앞 요소의 보안 그룹이나 접두사 목록만 인바운드 소스로 허용한다.
  • EC2 인스턴스는 Session Manager로 접속한다.

30초.

  1. 다음은 보안 그룹 설정을 나타냅니다. 각 구성 요소는 바로 앞 요소만 허용합니다.

  2. 외부 ALB는 클라우드프론트 주소 80번 포트만 허용합니다.

  3. WAS, RDS Proxy, RDS 역시 특정 포트만 허용합니다.

  4. 웹 서버와 WAS는 443번 포트로 VPC 엔드포인트에 접속할 수 있습니다.

  5. 참고로 EC2 인스턴스에는 Session Manager로 접속합니다.

(넘기며) 이제 이 기반 위에서 WAS를 어떻게 구축했는지 김건형 님이 설명하겠습니다.

질문 대비: 평문인 이유는 외부 ALB에 인증서를 두지 않아서다(오리진 프로토콜 HTTP only). WAS에서 RDS Proxy 구간은 TLS를 강제한다. 질문 대비: 패키지는 S3 게이트웨이 엔드포인트로 받는다(Amazon Linux 저장소, 팀 패키지 버킷). 질문 대비: CloudFront와 오류 페이지 S3 버킷 사이는 보안 그룹이 아니라 OAC와 버킷 정책으로 제한한다. 질문 대비: Session Manager는 서버의 SSM Agent가 ssm, ssmmessages 엔드포인트로 먼저 연결하는 방식이라 인바운드 포트가 필요 없다.

EC2 = Elastic Compute Cloud

WAS: 호환성 검토와 취약점 보완

보안

버전 호환성

  • 기존 Java 8과 javax 기반 소스에 맞춰 빌드와 운영 환경 구성
  • Tomcat 9.0.53 → 9.0.122, Spring Framework 5.3.9 → 5.3.39 업데이트
  • Spring BOM으로 모듈 버전 통일

취약점 보완

  • Spring 5.3.39의 DataBinder 관련 보안 취약점(CVE-2024-38820)에 입력 허용 필드 제한으로 대응
  • 다른 보호자의 반려동물 정보가 수정되지 않도록 보호자 관계 검증
  • 변경한 기능을 테스트로 검증한 뒤 WAR 파일 빌드

안녕하세요. 이번 팀프로젝트에서 WAS 구축을 맡은 김건형입니다. 먼저 기존 Java 8과 javax 기반 소스에 맞춰 환경을 구성하고, Tomcat과 Spring을 화면에 보이는 버전으로 업데이트했습니다.
업데이트한 Spring 버전도 DataBinder 관련 보안 취약점이 있어 입력 허용 필드를 제한했고, 반려동물 정보를 수정할 때 해당 보호자의 반려동물인지 검증하도록 했습니다. 코드를 수정한 뒤 기존 테스트가 모두 통과하는지 확인했고, WAR 파일도 정상적으로 빌드했습니다.

BOM = Bill of Materials CVE = Common Vulnerabilities and Exposures WAR = Web Application Archive

WAS: ARM 아키텍처 기반 배포와 설정 외부화

비용 최적화

ARM 아키텍처 기반 배포

  • AWS가 제공하는 Amazon Linux 2023 사용
  • 비용과 효율을 고려해 Graviton 기반 t4g.small 선택
  • ARM 아키텍처에서 Java 8과 Tomcat 9.0.122 동작 확인
  • AWS Systems Manager로 WAR 파일 배포 후 Petclinic 기동과 DB 연결 점검

운영 설정과 외부화

  • EC2 부팅 시 Tomcat 자동 시작
  • DB 접속 설정은 Parameter Store에서 조회
  • DB 계정 정보는 Secrets Manager JDBC 드라이버로 조회
  • 접속 설정 변경 시 WAR 재배포 없이 Tomcat 재기동만으로 반영
  • AMI와 시작 템플릿에 서버 설정 반영

서버에는 AWS가 제공하는 Amazon Linux 2023을 사용했고, 비용과 전력 효율을 고려해 Graviton 기반 t4g.small을 선택했습니다. ARM 아키텍처에서 Java 8과 Tomcat이 정상적으로 동작하는지 확인한 다음, AWS Systems Manager로 WAR 파일을 배포해 Petclinic 실행과 DB 연결을 점검했습니다. EC2 부팅 시 Tomcat도 자동시작 설정. DB 접속 설정은 소스에서 분리해 Parameter Store에 두고, 계정 정보는 Secrets Manager에서 관리하도록 했습니다. 그래서 설정이 바뀌어도 WAR를 재배포하지 않고 Tomcat을 재시작해 반영할 수 있습니다. 이 서버 구성은 AMI와 시작 템플릿에도 적용했습니다.

JDBC = Java Database Connectivity AMI = Amazon Machine Image

모니터링과 알림

  • CloudWatch Agent로 메모리 사용률 수집
  • 정상 WAS가 두 대 미만이면 CloudWatch 경보와 SNS 이메일 알림
  • 응답 WAS와 타겟그룹 상태를 보여주는 대시보드 구현

WAS를 두 곳의 az에 나눠 가용성을 높이고, ALB로 요청을 분산했습니다. ASG는 CPU 사용률에 따라 서버 수를 조절합니다. 운영 상태를 확인하기 위해 CloudWatch Agent로 메모리 사용률을 수집하고, 정상 WAS가 두 대 미만이면 이메일 알림을 받도록 했습니다. 현재 응답한 WAS와 타겟그룹 상태를 확인할 수 있는 대시보드를 만들었습니다.

ASG = Auto Scaling Group CPU = Central Processing Unit SNS = Simple Notification Service

DB 서버: RDS MySQL과 RDS Proxy

안정적인 DB 운영을 위해 가용성과 연결 안정성을 중점적으로 고려했다.

RDS for MySQL 8.4

  • Multi-AZ: AZ 2a Primary / AZ 2c Standby (동기 복제)
  • MySQL 8.4 LTS: 장기 지원과 유지보수 고려
  • 인스턴스: db.t4g.small / gp3 20 GiB
    • 연결 사용률: micro 93% / small 56%
    • 최소 가용 메모리: micro 91 / small 555 MiB
  • 데이터 보호: 자동 백업 7일 / KMS 스토리지 암호화

RDS Proxy

  • 연결 경로: WAS → RDS Proxy → RDS
  • 연결 풀링과 재사용: WAS 확장 시 DB 연결 증가 대응
  • 장애 대응: Multi-AZ 장애 조치 시 DB 연결 복구 지원
    • DB 쿼리 복구 시간: 135초 → 13초
  • TLS 필수: DB 인증 정보와 전송 데이터 보호

안녕하십니까. 데이터베이스 구축을 담당한 우수빈입니다.

저희는 안정적인 DB 운영을 위해 가용성과 연결 안정성에 중점을 두었습니다.

먼저 장애에 대비해 Multi-AZ를 적용하고, 장기적인 유지보수를 고려해 MySQL 8.4 LTS를 선택했습니다.

인스턴스는 비용 효율적인 t4g 계열을 검토했으며, 사전 부하 테스트에서 micro는 연결 사용률이 93%로 최대 연결 수에 근접했고, 최소 가용 메모리도 91MiB까지 감소했습니다. 반면 small은 연결 사용률 56%, 가용 메모리 555MiB로 상대적으로 여유가 있어 t4g.small을 선정했습니다.

또한 WAS 확장으로 DB 연결이 늘어나는 상황에 대비해 RDS Proxy를 적용했습니다.

이후 Multi-AZ 강제 장애 조치 후 쿼리를 반복 실행하며 복구 시간을 측정했습니다. 그 결과 직접 연결은 135초, Proxy 연결은 13초로, 복구 시간 약 90% 줄인 효과를 확인할 수 있었습니다.

웹 서버: Apache 리버스 프록시

<VirtualHost *:80>
    ProxyAddHeaders On
    ProxyPreserveHost On
    RewriteEngine On
    # /petclinic 으로 오면 /petclinic/ 으로 301
    RewriteRule ^/petclinic$ https://%{HTTP_HOST}/petclinic/ [R=301,L]
    # ttl=55: ALB 유휴 제한(60초)보다 먼저 닫는다
    # addressttl=30: ALB IP가 바뀌어도 30초 안에 다시 조회
    ProxyPass        "/petclinic/" "http://<INTERNAL_ALB_DNS>/petclinic/" ttl=55 addressttl=30
    ProxyPassReverse "/petclinic/" "http://<INTERNAL_ALB_DNS>/petclinic/"
</VirtualHost>
  • /petclinic/만 WAS로 넘기고, 나머지는 Apache가 직접 응답
  • 내부 ALB는 IP가 아니라 DNS 이름으로 가리킨다.
  • SELinux에서 httpd_can_network_connect 허용

45초. ttl을 ALB 유휴 시간보다 짧게 두는 이유(ALB가 먼저 끊은 연결을 다시 쓰면 502)를 한 문장으로.

웹 서버: CloudFront와 외부 ALB 보호

CloudFront (정액 요금제 Free)

  • 사용자 구간만 HTTPS. ALB에는 인증서가 없어 오리진은 HTTP
  • 동적 페이지라 캐싱 비활성화, 쿼리 문자열과 쿠키는 모두 전달
  • 오류 시 S3의 공통 오류 페이지 (/pet_*, OAC)
  • WAF 속도 제한: IP마다 5분에 300건 (현재 모니터 모드)

외부 ALB에 CloudFront만 닿게

  1. 보안 그룹: CloudFront 관리형 접두사 목록만 허용
  2. 리스너: 비밀 헤더를 포함한 요청만 전달, 나머지는 403

접두사 목록은 다른 사람의 CloudFront 배포도 통과시킨다. 비밀 헤더가 우리 배포만 골라낸다.

45초. VPC 오리진을 쓰면 ALB를 internal로 둘 수 있지만 정액 요금제 Business(월 200 USD) 이상이 필요해서 internet-facing ALB + 두 겹 보호를 택했다고 말한다.

HTTP = Hypertext Transfer Protocol OAC = Origin Access Control
